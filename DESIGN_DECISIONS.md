# Проектные решения безопасности

Решения развивают [паспорт](PROJECT.md), [требования безопасности](SECURITY_REQUIREMENTS.md)
и [модель угроз](THREAT_MODEL.md). Они охватывают весь приоритетный набор S04:
T-01 через D-02, T-03 и T-04 через D-03, T-05 и T-06 через D-01.
Дополнительные связи ниже сохраняют требования для остальных угроз.

**Статус комплекта:** предметная часть D-01 уже реализована. Защита хранения,
аутентификация и политика доступа описаны как следующие шаги реализации.
Запуск `/health` и создание SQLite подтверждают работоспособность технической
основы, но не подтверждают эти защитные свойства. Новые детали D-01 требуют
содержательной проверки M1; D-02 и D-03 подготовлены для проверки M2.
Подготовка текста с ИИ и фактическая проверка участниками отражаются отдельно
в [AI_USAGE.md](AI_USAGE.md).
M3 сообщил о проверке подготовленного комплекта вместе с технической основой;
это не заменяет самостоятельного понимания связанных решений M1 и M2 на защите.

## D-01. Предметные действия и согласованное сохранение заявки с историей

**Статус:** отдельная предметная модель, действия, события и модульные тесты
реализованы на основе решений M1. SQL-сохранение, версия записи и интеграционные
проверки ещё не реализованы. Проверка версии конкретизирует ранее выбранное
направление защиты от конкурентных обновлений.

**Контекст:** клиент может пропустить или повторить этап, а два допустимых
запроса — одновременно прочитать одну версию заявки. Например, одобрение и
отклонение по отдельности допустимы для `SUBMITTED`, но оба не должны стать
результатом одной исходной версии. Сбой между записью состояния и события
также делает историю недостоверной. Проверки только внутри одного Python-объекта
эти два случая хранения не решают.

**Решение:**

1. `PurchaseRequest` предоставляет действия `submit`, `approve`, `reject`,
   `place_order`, `complete`. Нет команды произвольного присваивания состояния.
   Допустимы только `SUBMITTED → APPROVED → ORDERED → COMPLETED`
   и `SUBMITTED → REJECTED`; оба конечных состояния закрыты для новых действий.
2. Успешное действие проверяет входные данные до изменения объекта и создаёт
   одно неизменяемое `HistoryEvent`. `submit` создаёт первую пару заявки и события;
   `restore` загружает сохранённое состояние без нового события.
   UUID создаётся до записи, время с часовым поясом и действующий пользователь
   передаются прикладным сервисом из доверенных источников.
3. Будущий прикладной сервис сначала проверяет полномочия по D-03, затем
   вызывает предметный метод. При создании репозиторий вставляет заявку и её
   событие в одну SQL-транзакцию. При изменении он выполняет условный
   `UPDATE ... WHERE id = :id AND version = :expected_version`, сохраняя новое
   состояние, номер заказа и `version = version + 1`. Ожидаемая версия
   берётся из загруженной строки БД, а не из произвольного поля клиента.
4. Только при изменении ровно одной строки репозиторий добавляет событие
   в той же транзакции и делает один `commit`. Нулевое число изменённых строк
   означает конфликт: выполняется `rollback`, событие не сохраняется,
   API возвращает `409 Conflict`. При любой ошибке записи откатывается вся
   транзакция; изменённый предметный объект больше не используется.
5. Повтор сохранённой команды перехода загружает новое состояние и получает `409`
   без нового события. Это запрет повторного перехода, а не возвращение
   прежнего успешного ответа по ключу идемпотентности. Потерянный ответ после
   успешного `commit` не отменяет результат: клиент проверяет состояние чтением.
6. Публичных операций изменения или удаления истории не будет. В API не
   принимаются автор, время, исходное и целевое состояние события.
   Предметные ошибки отображаются в безопасные `409`/`422`, ошибки хранения —
   в безопасный ответ без SQL, пути к БД и текста внутреннего исключения.

**Обоснование и альтернативы:** предметная модель оставляет правила переходов
в одном месте и проверяется без сервера и БД. Проверки, распределённые по
маршрутам, проще начать, но легко разойтись в повторных действиях и истории.
Универсальный движок переходов добавляет конфигурацию и способы ошибочного
расширения для фиксированного автомата из пяти состояний. Поэтому сохранены
осмысленные методы и отдельный прикладной сервис, выбранные M1.

Транзакция обеспечивает совместный результат состояния и истории; условная
запись версии дополнительно проверяет, что решение принято по актуальной
заявке. Одна транзакция с обычным безусловным `UPDATE` этого не гарантирует:
оба обработчика могли ранее прочитать `SUBMITTED`. Блокировка Python-процесса
не защищает другой процесс. Глобальная блокировка записи SQLite на всё время
чтения и проверки сериализует и несвязанные заявки; проверка версии выражает
нужную гарантию непосредственно для изменяемой строки.

**Связанные угрозы:** [T-05], [T-06]; дополнительно [T-02], [T-07], [T-10].

**Связанные требования:** [SR-06], [SR-07]; источник участника — [SR-02],
причина и номер заказа — часть [SR-10], безопасные ошибки — [SR-08].

**Будущая проверка:**

- **Условие:** сохранённые заявки во всех пяти состояниях; у вызывающего
  пользователя есть нужные полномочия. **Действие:** через API выполнить каждый
  разрешённый и запрещённый переход, включая повтор заказа и действия после
  отклонения/завершения. **Ожидаемый результат:** разрешённое действие даёт
  следующий статус и ровно одно событие; запрещённый переход после успешной
  проверки полномочий даёт `409` и сохраняет прежние данные. Для недоступного
  объекта раньше срабатывает отказ D-03 (`404`/`403`), также без изменений.
  Это интеграционное продолжение имеющейся предметной матрицы.
- **Условие:** два независимых подключения к одному временному файлу SQLite
  загрузили одинаковую версию `SUBMITTED`. **Действие:** барьером синхронизировать
  попытки одобрения и отклонения; повторить опыт с двумя разными номерами заказа
  для одной `APPROVED`. **Ожидаемый результат:** ровно один успешный переход,
  проигравший получает `409`, версия увеличилась один раз, в БД одно новое
  событие и номер заказа победившей команды. Обычная последовательность
  вызовов не заменяет эту проверку.
- **Условие:** новая заявка либо сохранённая заявка перед допустимым переходом.
  **Действие:** внедрить сбой после записи заявки/`UPDATE`, перед вставкой
  события и перед `commit`; завершить транзакцию и открыть БД новым подключением.
  **Ожидаемый результат:** нет частично сохранённой пары. После контролируемого
  отказа видна прежняя версия; после успешного `commit` — новая заявка/версия
  и соответствующее событие вместе, согласно [SR-07].
- **Условие:** переход зафиксирован, но HTTP-ответ потерян. **Действие:** снова
  отправить ту же команду и затем прочитать заявку и историю.
  **Ожидаемый результат:** повтор получает `409`; исходный успешный результат
  сохранён, нового события и перезаписи номера нет.

**Уже имеющееся подтверждение:** [модель](src/wildburny/domain/requests.py)
и [модульные тесты](tests/domain/test_request_lifecycle.py) проверяют переходы,
события и сохранность объекта при предметном отказе. Результаты их выполненных
запусков приведены в [AI_USAGE.md](AI_USAGE.md#проектирование-и-реализация-предметного-жизненного-цикла-заявки).
Эти тесты не проверяют SQL, конкурентность, полномочия или HTTP-коды.

**Ограничения и последствия:** версия записи относится к адаптеру хранения
и не требует изменения публичного предметного контракта. Все будущие пути
записи обязаны использовать один репозиторий и увеличивать версию; обход этого
правила разрушает гарантию. Ошибка блокировки SQLite сама по себе не означает
конфликт версии: обработчик откатывает транзакцию и после повторного чтения
может вернуть `409`, только если наблюдает изменённую версию. Иная ошибка БД
завершает команду безопасным отказом без частичных записей; автоматический
повтор не должен переигрывать уже сохранённую команду. Неизменяемый объект
события не защищает от прямого изменения файла БД доверенным локальным оператором.

## D-02. Серверная аутентификация и доверенный контекст пользователя

**Статус:** проектное решение для будущей реализации; аутентификация, таблица
пользователей и описанные проверки отсутствуют. Стек взят из паспорта,
детали контракта подготовлены для содержательной проверки M2.

**Контекст:** внешний клиент управляет заголовком, телом и параметрами запроса.
Наличие похожего на токен значения не устанавливает личность. Даже корректно
подписанный токен не должен позволять выбрать автора или отдел из тела команды.
Учебные пользователи создаются локально; регистрации и внешнего поставщика
идентичности в границе продукта нет.

**Решение:**

1. Пароли заранее созданных пользователей хранятся только как хеши Argon2
   через `pwdlib`; вход проверяет пароль по серверной записи. При неверном
   логине или пароле возвращается одинаковый безопасный отказ без учётных данных.
2. После входа сервер выдаёт ограниченный по времени JWT через PyJWT.
   Планируемый контракт: подпись HS256 с отдельным секретом конфигурации,
   `sub` — идентификатор пользователя, срок действия 15 минут, обязательные
   `exp`, `iss = wildburny`, `aud = wildburny-api`. Алгоритм и ожидаемые
   issuer/audience задаёт сервер; они не выбираются из недоверенного заголовка.
   Отсутствующий секрет не заменяется встроенным значением. Секрет и токены
   не входят в репозиторий, ответы об ошибках или журналы запросов.
3. Общая зависимость FastAPI для всех предметных маршрутов проверяет подпись,
   алгоритм, срок, обязательные claims и корректность `sub`, затем загружает
   существующего пользователя из БД. Неуспех любого шага даёт `401` до
   выполнения предметной операции. Исключения — только `/health` и вход.
4. Идентификатор пользователя, роль и отдел прикладной сервис берёт из этой
   серверной записи. Роль и отдел не принимаются из запроса и не используются
   из JWT как самостоятельный источник полномочий. Создание заявки использует
   `current_user.id`/`department_id`; участник истории — того же пользователя,
   время — серверное UTC. Начальное состояние задаёт `submit`.
5. Pydantic-схемы команд перечисляют разрешённые клиентские поля и запрещают
   дополнительные поля (`extra="forbid"`). Попытка передать служебные поля
   отклоняет всю команду. Формирование ответов валидации исключает исходные
   пароли, токены и внутреннюю диагностику согласно [SR-08].

**Обоснование и альтернативы:** общая зависимость исключает расхождение
проверок между маршрутами, а чтение пользователя из БД сохраняет роль и отдел
доверенными и актуальными на начало обработки. Альтернатива — хранить все
полномочия в токене и не читать БД: меньше запросов, но изменение роли/отдела
не действует до истечения токена. Непрозрачная серверная сессия тоже допустима
и даёт прямой отзыв сессии, но требует дополнительного хранилища сессий;
для локального API сохранён выбранный в паспорте JWT. Argon2 снижает риск
восстановления пароля по утёкшему хешу; он не заменяет проверку токена и D-03.

**Связанные угрозы:** [T-01]; дополнительно [T-02], [T-07], [T-08].

**Связанные требования:** [SR-01], [SR-02], [SR-08].

**Будущая проверка:**

- **Условие:** доступны все будущие предметные маршруты и существующая
  учётная запись. **Действие:** вызвать каждый маршрут без токена, с повреждённой
  подписью, истёкшим сроком, отсутствующим claim, неверными алгоритмом,
  issuer/audience, некорректным или несуществующим `sub`.
  **Ожидаемый результат:** `401`, нет предметных данных и изменений БД;
  `/health` остаётся доступным без токена. Валидный токен доходит до D-03.
- **Условие:** токен сотрудника и другой пользователь/отдел в БД.
  **Действие:** добавить в создание заявки чужого автора, отдел, роль,
  состояние, время или участника события; отдельно поменять роль/отдел
  пользователя в серверных учебных данных и повторить запрос со старым токеном.
  **Ожидаемый результат:** служебные поля дают отказ без заявки и события;
  при нормальной команде используются актуальные серверные данные.
- **Условие:** неверные учётные данные и токены с контрольными строками.
  **Действие:** выполнить вход и вызвать защищённый маршрут; проверить ответы
  и захваченные журналы. **Ожидаемый результат:** контрольных паролей/токенов,
  хешей и внутренних исключений нет; в БД отсутствуют открытые пароли.

**Ограничения и последствия:** подпись JWT не шифрует содержимое, поэтому
в claims нет сведений о заявках и секретов. Отдельный отзыв конкретного токена
и refresh-токены пока не предусмотрены; украденный токен существующего
пользователя действует до истечения срока, а смена секрета отзывает все токены.
Чтение пользователя выполняется на каждом запросе. Гонки с административной
сменой ролей не входят в локальные сценарии без административного API.
Защита от перебора, HTTPS и политика хранения токена потребуют отдельного
решения перед сетевым размещением; текущий запуск ограничен локальной машиной.

## D-03. Единая политика чтения и исполнения команд

**Статус:** проектное решение для будущей реализации и проверки M2. Правила
соответствуют SR-03–SR-05 и SR-09; работающая политика и предметные HTTP-маршруты
ещё не реализованы. Допустимость перехода отдельно обеспечивает D-01.

**Контекст:** действительный токен не даёт полномочий на любую заявку.
Проверка роли без владельца/отдела раскрывает чужие данные; проверка только
отдельной заявки оставляет обход через список или историю. Закупщику нужен
доступ всех отделов, но только после одобрения.

**Решение:** единая серверная политика получает пользователя из D-02 и
сохранённые поля заявки. Прикладной сервис применяет её перед выдачей данных
и перед вызовом предметного действия. Неизвестная роль или действие запрещены.

| Операция | Условие доступа |
| --- | --- |
| Создание заявки | Роль сотрудника; автор и отдел из D-02 |
| Чтение сотрудником | `request.author_id == current_user.id` |
| Чтение руководителем | `request.department_id == current_user.department_id` |
| Чтение закупщиком | Состояние `APPROVED`, `ORDERED` или `COMPLETED` любого отдела |
| Одобрение / отклонение | Роль руководителя и совпадение отдела |
| Заказ / завершение | Роль закупщика; допустимость состояния проверяет D-01 |

Политика чтения задаёт серверный предикат запроса к БД. Список выбирается
с этим предикатом; клиентские фильтры могут только дополнительно сузить его.
Отдельная заявка выбирается по ID с тем же ограничением. История доступна
только после проверки чтения родительской заявки; её ID не открывает обход.
Недоступная и отсутствующая заявка дают одинаковый безопасный `404`.
Для видимой заявки запрещённая роли команда даёт `403` до предметного вызова;
при разрешённых полномочиях неверное состояние даёт `409` по D-01.

Схема каждой команды содержит только нужные этой команде значения. Изменять
содержание после отправки нельзя. При создании количество и сумма в копейках
принимаются как строгие положительные целые числа (без `bool` и преобразования
строк/дробей), обязательные тексты нормализуются и проверяются по [SR-10].
Причина отклонения и номер заказа дополнительно проверяются предметной моделью.
Эти проверки выполняются до сохранения; ошибки не добавляют событие.

**Обоснование и альтернативы:** одна политика и одинаковое ограничение
выборки связывают список, объект и историю с одними правилами. Альтернатива —
независимые проверки в каждом маршруте — позволяет забыть одно из трёх мест
чтения. Фильтрация только в клиенте не защищает прямой HTTP-запрос; скрытые UUID
тоже не являются полномочием. Проверка только роли допускает руководителя
другого отдела и закупщика к `SUBMITTED`/`REJECTED`. Разделение политики и
автомата сохраняет две независимые причины отказа: кто вправе действовать
и допустимо ли действие в текущем состоянии.

**Связанные угрозы:** [T-03], [T-04]; дополнительно [T-08], [T-09], [T-10].

**Связанные требования:** [SR-03], [SR-04], [SR-05], [SR-09], [SR-10];
источник полномочий — [SR-02], безопасные ответы — [SR-08].

**Будущая проверка:**

- **Условие:** два отдела, два сотрудника одного отдела, руководители обоих
  отделов, закупщик и заявки каждого состояния. **Действие:** каждой ролью
  запросить список, отдельную заявку и историю; подставить известный чужой ID
  и менять клиентские фильтры. **Ожидаемый результат:** сотрудник видит только
  свои записи, руководитель — свой отдел, закупщик — три разрешённых состояния
  независимо от отдела. Недоступные и отсутствующие ID дают одинаковый `404`.
- **Условие:** заявка в состоянии, допускающем проверяемую команду.
  **Действие:** сотрудником, закупщиком и руководителем другого отдела вызвать
  одобрение/отклонение; сотрудником и руководителем — заказ/завершение.
  **Ожидаемый результат:** отказ `403` для видимого объекта либо `404` для
  недоступного; прежние состояние, номер и история сохранены. Положительные
  случаи проходят только для роли и отдела из таблицы.
- **Условие:** закупщик не видит `SUBMITTED`. **Действие:** уполномоченным
  руководителем одобрить заявку, затем пройти заказ и завершение.
  **Ожидаемый результат:** закупщик получает чтение после одобрения и сохраняет
  его после завершения; отклонённая заявка чтения ему не предоставляет.
- **Условие:** допустимые создание и команды уполномоченного пользователя.
  **Действие:** повторить отрицательную матрицу [SR-10], затем передать новое
  корректное содержание в разрешённую команду обработки.
  **Ожидаемый результат:** `422` без сохранения и без события; правильные
  значения не позволяют изменить уже отправленную покупку. Ответы не содержат
  полей недоступной заявки и внутренней диагностики.

**Ограничения и последствия:** SQL-условия списка и проверка отдельного объекта
должны сохранять одну семантику, что требует общего набора тестовых данных.
Новые пути экспорта или выдачи истории обязаны включаться в эту же политику.
`404` скрывает существование недоступной заявки в обычном ответе, но не доказывает
отсутствие всех побочных каналов. Схема содержания покупки и проверки его
неизменности пока не входят в реализованный предметный пакет; их ещё нужно
добавить при реализации сценария создания.
